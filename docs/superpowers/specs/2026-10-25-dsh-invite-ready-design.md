# Ball Chess DSH 邀请、准备与自动对局设计

- 日期：2026-10-25
- 状态：已在对话中逐节批准，待用户审阅书面规格
- 代码归属：`ball_chess` 仓库
- 集成方式：Ball Chess 专用 DSH 桥接插件与 Agent 预设

## 1. 目标

用户只需为一个明确席位生成邀请码，然后在使用 Ball Chess Agent 预设的 DSH 对话中输入“加入邀请码 ABC123 并开始”。Agent 应兑换席位、准备、等待对手并持续完成整场对局。人类玩家和 Agent 使用同一个后端准备状态；双方都准备后，服务端才开始比赛。

该设计必须同时支持两个 DSH Agent 对战、Agent 与人类对战、进程重连和凭证恢复，并保证不同 DSH 对话不会共享席位或串局。玩家 token 不进入模型输入、工具结果或 Session 日志。

## 2. 已确认的产品决策

- 主要用户流程使用十分钟有效的一次性邀请码。
- 邀请码绑定到某场对局的明确席位；左、右席位分别生成，不能由 Agent 抢占任意空位。
- 每个席位最多有一个有效邀请码；生成新邀请码会使旧邀请码立即失效。
- 邀请成功兑换后立即失效；相同幂等兑换请求可安全重试。
- 现有 `matchId + playerToken` 预绑定 MCP 入口继续保留，用于测试、自动化和手工故障恢复。
- `joined` 与 `ready` 是不同状态。加入只占用席位并记录玩家资料，不再触发开局。
- 已加入玩家可以在等待阶段准备或取消准备；双方都准备后原子进入 `playing`，此后不能取消。
- 准备状态持久化。页面刷新、网络断开、MCP 重连和子进程替换不会自动取消准备。
- 一个 DSH 对话同一时间只绑定一场未结束对局。对局结束后才能兑换下一场邀请码。
- 用户发出一次开始指令后，正常运行期间 Agent 持续等待和行动直到对局结束，不要求每回合人工唤醒。
- MCP 子进程故障时自动重连并继续当前 DSH turn。整个 DSH 应用重启后恢复席位凭证，但不自动产生新的模型调用；用户在原对话输入“继续对局”后续跑。

## 3. 方案选择

### 3.1 预绑定与邀请码

预绑定实现简单且权限明确，但每场对局都需要生成并安装新的 MCP 配置，不适合作为长期使用的 Agent 预设。一次性邀请码使预设只需安装一次，之后每场只输入邀请码。采用邀请码作为主要流程，同时保留预绑定兼容入口。

### 3.2 通用 MCP 客户端与专用桥接插件

DSH 的 Agent 预设修订由多个 Agent 共享，直接放在预设中的普通 `@deepseek-ai/dsh-mcp-client` 实例也会共享连接。通用 MCP 桥接只转发模型工具参数，不把当前 `ToolExecution.agent` 身份发送给 MCP 服务器，因此一个进程内的隐式席位绑定无法可靠地区分多个 DSH 对话。

不采用让模型在每次调用中传递 `bindingId` 的方案，因为它容易串局，并把会话隔离职责交给提示词。不采用每个 Agent 启动一套 DSH 的方案，因为它增加运行和配置负担。

采用 Ball Chess 专用 DSH 桥接插件。插件读取 `ToolExecution.agent`，按 DSH Session 隔离 MCP 客户端与凭证，并由 Ball Chess Agent 预设装配。该插件属于 `ball_chess`，不向通用 `deepseek-harness` 仓库加入游戏专用代码。

## 4. 总体架构

```text
Ball Chess 前端 ── 创建席位邀请 / 人类 ready ──┐
                                                  ▼
                                            Ball Chess 后端
                                                  ▲
DSH 对话 ── Ball Chess Agent 预设 ── 专用桥接插件 ── 每 Session 独立 MCP 客户端
                                                  │
                                                  └── DSH 凭证存储
```

Ball Chess 后端是邀请、席位、准备、开局和棋局状态的唯一权威。MCP 不复制规则或准备状态。DSH 插件负责把当前 DSH Session 映射到一个席位凭证和一个 MCP 客户端。Agent 预设只负责组合插件、工具和行为说明。

前端、MCP 和 DSH 插件都调用相同的后端 `/ready` 语义。前端按钮不是独立状态，也不能在本地推断开局。

## 5. 后端记录与状态迁移

### 5.1 对局记录

持久化对局记录新增以下信息：

```json
{
  "ready": { "left": false, "right": false },
  "invitations": {
    "left": null,
    "right": {
      "digest": "<摘要>",
      "expiresAt": 0,
      "consumedAt": null,
      "redemptionId": null
    }
  }
}
```

邀请只保存不可逆摘要，不保存明文邀请码。兑换成功后保存消费时间和幂等兑换标识，以便响应丢失后使用相同标识恢复结果。对外状态、棋谱导出和日志不包含邀请摘要、玩家 token 或兑换内部信息。

持久化记录格式版本随字段变更升级。旧版本记录恢复时明确补充 `ready.left = false`、`ready.right = false` 和空邀请状态。旧记录中双方已加入不意味着已经准备，也不能因加载记录自动开局。

### 5.2 状态迁移

创建对局后状态为 `waiting`，两个席位均未加入、未准备。兑换邀请码或使用现有玩家 token 调用 `/join` 只设置对应 `joined` 和玩家资料。加入不会改变另一席位，也不会启动回合计时。

只有已加入席位能修改自己的准备状态。等待阶段可在 `true` 与 `false` 之间切换；重复写入相同值是幂等操作。第二个席位变为 ready 时，同一次原子更新必须完成以下操作：保留双方 ready、切换状态到 `playing`、结算首回合可行动性、设置回合截止时间并将版本递增一次。提交成功后再广播 SSE 快照。

进入 `playing` 或 `finished` 后，准备状态不再可修改。断开连接不是状态迁移，不清除 `joined` 或 `ready`。

若人类通过既有玩家 token 占用了一个仍有有效邀请的席位，该席位邀请同时失效。管理员中止对局时，所有未兑换邀请失效。

## 6. 邀请和准备 API

### 6.1 生成邀请

`POST /api/matches/:matchId/invitations`

- 使用管理员 Bearer token。
- 请求体为 `{ "seat": "left" | "right" }`。
- 仅允许等待中且尚未加入的席位。
- 成功时返回一次明文邀请码、席位和 `expiresAt`。
- 明文邀请码由 128 位密码学安全随机值编码为 26 个 Crockford Base32 字符，并以连字符分组展示。输入比较不区分大小写并忽略连字符；后端只保存规范化值的 SHA-256 摘要。
- 再次生成会原子替换旧邀请。

### 6.2 兑换邀请

`POST /api/invitations/redeem`

请求包含邀请码、Agent 显示名、客户端类型和 DSH 插件生成的幂等兑换 ID。一次事务完成邀请校验、过期检查、席位占用检查、加入资料写入、邀请消费记录和持久化。响应向可信的 DSH 插件返回 `matchId`、席位、玩家 token 与最新状态。

相同邀请码和相同兑换 ID 的重试返回相同绑定结果。邀请码已经由不同兑换 ID 成功使用时返回 `INVITE_CONSUMED`。并发兑换只能有一个不同兑换 ID 成功。

### 6.3 设置准备

`POST /api/matches/:matchId/ready`

- 使用玩家 Bearer token。
- 请求体为 `{ "ready": true | false }`。
- 未加入返回明确错误。
- 只允许在 `waiting` 修改。
- 响应返回席位视角的最新状态。

公共状态的 `seats.left` 和 `seats.right` 增加 `ready`。所有浏览器和 Agent 都以服务端返回值更新显示。

## 7. DSH 插件、凭证和 MCP 生命周期

### 7.1 Session 隔离

桥接插件从每次工具执行的 `ToolExecution.agent` 取得稳定 Session 身份。运行中的 MCP 客户端以 Session 身份索引，不以预设 ID、模型 ID 或进程全局变量区分。两个使用相同预设的 DSH 对话必须得到不同客户端和不同席位状态。

插件为每个 Session 保存版本化记录。兑换请求发出前先保存待处理记录：

```json
{
  "version": 1,
  "state": "redeeming",
  "baseUrl": "http://127.0.0.1:7100",
  "inviteCode": "<secret>",
  "redemptionId": "<128-bit random id>"
}
```

后端确认兑换后，原子替换为已绑定记录：

```json
{
  "version": 1,
  "state": "bound",
  "baseUrl": "http://127.0.0.1:7100",
  "matchId": "m_example",
  "seat": "left",
  "playerToken": "<secret>"
}
```

两种记录都由 DSH 凭证服务持久化并按 Session 寻址。待处理记录使未知结果能够使用原邀请码和兑换 ID 恢复；一旦写入已绑定记录就删除邀请码。用户输入的邀请码会进入 DSH Session，但它十分钟过期且兑换一次后失效；插件不得在工具结果或普通日志中再次回显邀请码。模型输出、工具结果、普通日志和 DSH Session 都不得包含长期有效的 `playerToken`。插件只有在恢复兑换、向后端认证或启动预绑定 MCP 子进程时读取秘密字段。

### 7.2 邀请兑换

`join_by_invite` 是桥接插件拥有的工具。插件在发送兑换请求前生成并持久保存兑换 ID；后端成功响应后，将席位凭证写入 DSH 凭证服务，再向模型返回去除 token 的状态。如果响应结果未知，插件使用相同兑换 ID 重试，不生成第二个兑换请求。

当前 Session 已绑定未结束对局时，`join_by_invite` 返回 `ALREADY_BOUND`。相同对局的恢复不要求再次提供邀请码。对局结束后，插件可以替换为下一场凭证。

### 7.3 MCP 子进程

取得席位凭证后，插件按 Session 懒启动独立 Ball Chess MCP stdio 子进程，使用现有 `--match` 和显式 `BALL_CHESS_PLAYER_TOKEN` 预绑定机制。预绑定子进程不向模型提供通用 `join_match`。

子进程意外退出时，插件使用同一凭证重新创建并恢复席位。创建、重连和工具同步采用 single-flight，避免同一 Session 的并发工具调用启动多个子进程。Agent 或 Session 被释放时关闭运行中的子进程；持久化凭证保留用于恢复。

整个 DSH 应用重启后，用户在原 Session 发起下一次 turn 时，插件读取凭证并恢复子进程。插件不在应用启动时自动调用模型或代替用户继续走棋。

## 8. Agent 工具与行为

新预设向模型提供以下工具：

| 工具 | 行为 |
|---|---|
| `join_by_invite` | 为当前 DSH Session 兑换邀请码并绑定指定席位 |
| `set_ready` | 在等待阶段设置或取消准备 |
| `get_match_state` | 返回压缩合法行动、ASCII 棋盘和席位准备状态 |
| `wait_for_turn` | 等待开局、轮到自己或对局结束 |
| `submit_action` | 使用 `expectedVersion` 提交移动或放墙 |

收到“加入邀请码 ABC123 并开始”后，Agent 依次调用 `join_by_invite`、`set_ready({ ready: true })` 和 `wait_for_turn`。对手未准备时保持等待；开局后不是自己的回合时继续等待；轮到自己时依据最新状态选择并提交合法行动，然后再次等待，直到 `finished`。

`wait_for_turn` 使用 SSE 等待有意义的状态变化。网络心跳、短暂断开和无变化重试由 MCP 内部处理，不向模型反复返回 `waiting: true`。工具在轮到自己、对局结束、调用被取消或发生不可恢复错误时才返回。桥接插件为等待调用使用单独的可配置长等待时限，不继承普通 MCP 调用的 60 秒默认值；达到时限后在插件内部重订阅，不向模型产生一次无变化结果。等待时不占用新的模型请求。

DSH 当前 turn 仍存在时，MCP 子进程重连后继续等待。整个 DSH 应用重启会中断 turn；用户输入“继续对局”后，Agent 直接读取已恢复状态，不再次兑换或重复准备。

## 9. 前端体验

等待阶段在左、右席位分别提供“生成 Agent 邀请码”。生成后显示邀请码和十分钟倒计时，并提供复制完整命令，例如：

```text
加入邀请码 ABCD-EFGH-JKLM 并开始
```

新生成邀请时，界面明确提示旧码已失效。邀请码兑换、过期或席位被其他方式占用后，前端根据 SSE 状态移除可用邀请提示。

人类席位使用同一个准备按钮切换 `ready`。按钮文字和禁用状态以服务端状态为准：等待阶段显示“准备”或“取消准备”，开局后锁定。席位区域同时显示 `未加入`、`未准备`、`已准备`、`对局中` 等本地化状态，不只依靠颜色表达。

## 10. 错误处理

后端与插件使用稳定错误码，并提供不会泄露凭证的行动建议：

| 错误码 | 处理 |
|---|---|
| `INVITE_INVALID` | 邀请不存在或格式错误；检查输入 |
| `INVITE_EXPIRED` | 在前端重新生成 |
| `INVITE_CONSUMED` | 其他兑换请求已使用；相同幂等 ID 重试不触发此错误 |
| `SEAT_OCCUPIED` | 选择另一个空席位或新对局 |
| `ALREADY_BOUND` | 完成当前对局后再加入下一场 |
| `MATCH_NOT_READY` | 准备完成前不能落子 |
| `MATCH_ALREADY_STARTED` | 开局后不能改变准备状态 |
| `STALE_STATE` | 使用返回的最新状态重新决策，不重放旧动作 |
| `ILLEGAL_ACTION` | 使用最新合法行动重新选择 |

临时网络失败不删除本地席位凭证，也不自动兑换新邀请。MCP 子进程恢复采用有界指数退避；失败达到配置上限后向 Agent 报告可重试错误。邀请码、玩家 token 和认证响应正文不得进入错误字符串或普通日志。

未知兑换结果必须通过原兑换 ID 查询或重试，不能把它报告为确定失败。凭证写入失败时，插件不得向模型报告加入成功；它保留待处理记录并执行恢复流程。

## 11. 测试设计

### 11.1 后端状态与 API

- `/join` 不再自动开局。
- 准备、取消、重复设置和未加入拒绝。
- 第二个 ready 只产生一次版本递增，并原子设置 `playing` 和首回合截止时间。
- 开局后拒绝取消准备。
- 指定席位邀请、十分钟过期和重新生成使旧码失效。
- 并发兑换只有一个不同兑换 ID 成功。
- 相同兑换 ID 在响应丢失后返回同一绑定。
- 人类占位、管理员中止和对局结束使未兑换邀请失效。
- ready、邀请消费和开局状态经过服务重启保持一致。
- 旧记录迁移为未准备，不会自动开局。

### 11.2 MCP 与 DSH 插件

- 两个模拟 `ToolExecution.agent` 使用同一预设时获得独立 MCP 客户端和不同席位。
- `join_by_invite` 的模型可见结果、Session 事件和日志不包含玩家 token。
- 已绑定 Session 拒绝不同邀请码；结束后允许下一场。
- 同一 Session 并发调用只创建一个子进程。
- 子进程崩溃后从凭证恢复并继续工具调用。
- DSH 重启模拟从相同 Session ID 恢复绑定，但不会主动触发工具或模型。
- `wait_for_turn` 在无变化期间不产生模型可见轮询结果，在准备、轮到自己、结束和取消时正确返回。
- SSE 断线后重新读取权威状态，不遗漏已经发生的回合变化。

### 11.3 前端与端到端

- 左右席位分别生成、复制、替换和过期邀请码。
- 人类准备按钮使用 `/ready` 并反映双方状态。
- 两个 Agent 分别兑换左右邀请码、准备、开局并交替行动。
- Agent 与人类混合对局使用同一准备和开局状态机。
- 两个 DSH 对话并行运行时不共享凭证、不串局。

## 12. 代码归属与交付

所有新增代码位于 `ball_chess` 仓库：后端邀请与准备逻辑、前端控件、MCP 等待与准备能力、DSH 桥接插件、Agent 预设配置、测试和使用文档。DSH 通过 Ball Chess 提供的配置补丁加载，例如：

```powershell
pnpm dsh web --patch E:\My_project\ball_chess\dsh\ball-chess.overlay.yml
```

配置补丁只使用 DSH 已有的公开插件与工具扩展接口。不修改 `deepseek-harness` 核心源码，不改变通用 `dsh-mcp-client` 的协议行为。

## 13. 范围外

- 自动搜索大厅或抢占任意空席位。
- 一个 DSH Session 同时参加多场未结束对局。
- DSH 应用启动时自动产生模型调用或无人值守恢复已中断 turn。
- 账号系统、公网邀请服务和跨设备凭证同步。
- 为通用 DSH MCP 客户端增加 Ball Chess 专用字段。
- 让模型读取、保存或传递玩家 token。

## 14. 完成判定

以下条件全部满足时，第二步完成：

1. 人类加入不再开局，双方 ready 才原子进入 `playing`。
2. 前端能为明确席位生成十分钟一次性邀请码，并能用同一接口准备或取消准备。
3. 使用 Ball Chess 预设的两个 DSH 对话可以分别通过邀请码绑定左右席位，不共享连接或凭证。
4. 玩家 token 不进入模型上下文、Session 日志、普通日志或公共状态。
5. 用户各发送一次开始指令后，两个 Agent 能等待、被对方准备唤醒并持续完成对局。
6. MCP 子进程故障能自动恢复；DSH 重启后原 Session 能在用户输入“继续对局”时恢复。
7. 并发兑换、响应丢失、旧记录迁移、准备状态持久化和两个 Agent 并行隔离均有自动化测试。

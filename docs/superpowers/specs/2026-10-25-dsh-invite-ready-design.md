# Ball Chess 席位、准备、前端流程与 DSH 接入设计

- 日期：2026-10-25
- 状态：依据前后端第一性原理复盘重写，待用户审阅书面规格
- 目标记录版本：v2
- 代码归属：`ball_chess` 仓库
- DSH 集成：Ball Chess 专用 Cordis 插件与 Agent 预设

本文取代此前的“第二步”设计，并修正 v1 方案中“加入即开局”、模型参与长期 token 传递、固定间隔轮询和默认展示两个席位凭证等设计。术语以仓库根目录的 `CONTEXT.md` 为准。

## 1. 问题与目标

Ball Chess 的核心不是连接两个客户端，而是可靠地维护一场由两个席位控制者参与的对局。浏览器、MCP 和 DSH 只是控制席位的不同客户端，任何一种客户端断线都不应改变席位归属、准备状态或棋局事实。

本方案需要同时做到：

- 人类和 Agent 使用同一种短期邀请认领明确席位。
- 人类点击“准备”和 Agent 调用 `set_ready` 产生完全相同的后端状态迁移。
- 两个 DSH 对话使用同一预设时仍有独立的席位凭证，不会串局。
- 用户输入“加入邀请码 ABC123 并开始”后，Agent 能认领、准备、等待并持续完成整场对局。
- 前端以创建、等待、进行、结束四个阶段组织任务，不把所有操作长期堆在一个页面上。
- 后端在并发、超时、持久化失败和重启恢复时保持唯一且可解释的权威状态。
- 长期玩家 token 不进入模型上下文、工具结果、Session 日志或公共状态。

### 1.1 非目标

- 公共账号、匹配大厅或自动搜索空席位。
- 一个 DSH Session 同时控制多场未结束对局。
- DSH 完整重启后自动发起模型调用；恢复后仍需用户在原对话输入“继续对局”。
- 修改 DSH 核心或通用 MCP 客户端以加入游戏专用逻辑。
- 引入数据库、WebSocket 或前端框架。当前单进程、JSON 文件、HTTP、SSE 和原生前端足以承载目标。
- 让模型读取、保存或传递玩家 token。

## 2. 第一性原理与系统约束

1. **后端是唯一权威。** 席位、准备、开局、轮次、截止时间、结果和棋谱都由后端确认；客户端只提交意图并显示确认后的状态。
2. **连接是临时事实。** SSE 断线、页面刷新或 MCP 客户端连接中断不撤销认领或准备。
3. **同一对局的命令必须串行。** 邀请兑换、准备、行动、超时和中止都进入同一 per-match 命令队列，不能各自读旧快照后竞争写入。
4. **截止时间是规则输入。** 若处理命令时 `now >= turnDeadlineAt`，先结算超时；同一时刻到达的行动不能越过已到期截止时间。
5. **持久化成功才算提交。** 状态迁移、保存、内存替换、计时器重设、通知必须按固定顺序执行；通知失败不能让已提交命令表现为失败。
6. **管理能力与席位能力分离。** 管理员可以生成邀请和中止对局，但不因管理身份自动控制任一席位。
7. **秘密最小暴露。** 邀请码可以出现在发起加入的 DSH Session 中，因为它短期且一次性；长期玩家 token 只保存在受插件控制的凭证记录中。

## 3. 领域状态与持久化记录 v2

### 3.1 权威记录

v2 对局记录包含以下概念字段：

```json
{
  "formatVersion": 2,
  "matchId": "m_example",
  "config": { "turnTimeoutMs": 60000 },
  "seats": {
    "left": { "phase": "open", "profile": null },
    "right": {
      "phase": "claimed",
      "profile": { "displayName": "Agent 2", "clientType": "dsh" }
    }
  },
  "invitations": { "left": null, "right": null },
  "actions": [],
  "result": null,
  "startedAt": null,
  "turnDeadlineAt": null,
  "createdAt": 0,
  "updatedAt": 0,
  "version": 1
}
```

不持久化重复的 `status` 字段。公共状态按以下规则派生：

- `result !== null`：`finished`；
- `result === null && startedAt !== null`：`playing`；
- 其余：`waiting`。

席位阶段为闭集：`open` 表示尚未认领，`claimed` 表示已认领但未准备，`ready` 表示已认领并准备。`profile` 只保存显示所需的非秘密资料。玩家 token 及其认证材料不进入公共记录投影、棋谱导出或普通日志。

### 3.2 必须始终成立的不变量

- `open` 席位的 `profile` 必须为空；`claimed` 和 `ready` 席位必须有 profile。
- 只有两个席位都是 `ready` 时才能首次设置 `startedAt`。
- `startedAt !== null` 后席位阶段固定为 `ready`，不可退回。
- 限时配置下的 `playing` 必须有当前回合截止时间；不限时配置以及 `waiting`、`finished` 不得有截止时间。
- `result !== null` 后不得再接受准备、邀请兑换或行动。
- 重放 `actions` 得到的棋盘、行动方和规则内结果必须与持久化字段一致。
- 如果重放仍未结束，持久化结果只能是超时或管理员中止这类规则外结果。
- `version` 在每个成功的权威命令中只递增一次。

### 3.3 v1 到 v2 的迁移

读取 v1 时先在内存中迁移并验证；下一次权威修改成功时写成 v2，不在读取时覆盖原文件。

- 原 `waiting`：`joined: false` 映射为 `open`，`joined: true` 映射为 `claimed`。
- 原 `playing`：已加入的两个席位映射为 `ready`，保留原截止时间；`startedAt` 优先取第一步行动时间，没有行动时取旧 `updatedAt`。
- 原 `finished`：若对局曾开始，两个已加入席位映射为 `ready` 并补齐 `startedAt`；未开始即中止的记录保留其实际席位阶段。
- 迁移后重放全部行动。棋盘、行动方或规则内结果矛盾时，将记录标记为不可用并报告原因，不覆盖文件，也不猜测修复。
- 旧记录已经处于 `playing` 或 `finished` 时不得重置成等待双方重新准备。

## 4. 后端命令模型

### 4.1 统一提交管线

每场对局拥有串行命令队列。创建后的所有修改都走同一管线：

```text
读取当前记录
  → 用注入时钟结算已到期超时
  → 校验命令和 expectedVersion
  → 计算下一记录并验证不变量
  → store.save(next)
  → 替换内存记录
  → 重设或取消计时器
  → 发布通知
```

`store.save` 失败时，内存状态、计时器和通知均保持原状。通知发生在提交之后并被隔离：某个 SSE 订阅者写入失败只关闭该订阅，不能让调用方收到“命令失败”。

计时器仅用于及时唤醒，不是超时正确性的来源。每条命令都用同一可注入时钟检查截止时间。`turnTimeoutMs` 的最大值限制为 `2_147_483_647`，避免 Node 定时器溢出后立即触发。

行动提交直接验证请求的那一个移动或放墙，不为判断合法性预先枚举整张棋盘所有可能墙位。完整合法行动列表只在确有客户端展示需求时按需生成。

### 4.2 创建对局

`POST /api/matches`

请求可包含 `config` 和可选的 `claim`。提供 claim 时，创建与认领自己的席位在一次提交中完成，避免“创建成功但随后认领失败”的半完成流程。响应返回管理员 token；若同时认领，只额外返回该席位自己的玩家 token。默认响应和前端不再展示两个席位 token。

### 4.3 生成邀请

`POST /api/matches/:matchId/invitations`

- 使用管理员 Bearer token，请求体为 `{ "seat": "left" | "right" }`。
- 只允许对等待中的 `open` 席位生成。
- 邀请十分钟有效，绑定明确对局和席位。
- 使用 128 位密码学安全随机值，编码为 26 个 Crockford Base32 字符；输入规范化为大写并忽略连字符。
- 后端只保存规范化邀请码的 SHA-256 摘要，不保存明文。
- 同一席位只保留一个有效邀请；新邀请原子替换旧邀请并增加邀请 generation。
- 公共状态只说明该席位是否存在有效邀请及 generation，不暴露摘要或明文。

### 4.4 兑换邀请

`POST /api/invitations/redeem`

请求包含 `code`、128 位 `redemptionId` 和非秘密 profile。兑换、席位认领、消费回执和保存必须在同一命令中完成。

幂等判断先于过期、对局结束和席位占用判断：若同一邀请码已由同一 `redemptionId` 成功兑换，重试必须返回原 `matchId`、席位、玩家 token 和最新公共状态，即使此时邀请码已过期或对局已经结束。若由不同 ID 消费，返回 `INVITE_CONSUMED`。

成功回执至少保留到对局被显式删除，以支持响应丢失和进程重启后的确定性恢复。邀请码摘要索引可以从记录重建，只用于定位候选对局，不能成为消费状态的独立权威。

### 4.5 准备与开局

`POST /api/matches/:matchId/ready`

- 使用玩家 Bearer token，请求体为 `{ "ready": true | false }`。
- 只有 `claimed` 席位能变为 `ready`；等待阶段可从 `ready` 取消为 `claimed`。
- 重复写入相同值成功返回当前状态，不额外递增版本。
- 第二个席位变为 `ready` 的同一原子提交中设置 `startedAt`、结算初始局面可行动性并建立首回合截止时间。
- 开始或结束后不可改变准备状态。
- 断线、刷新和客户端退出都不修改准备状态。

现有以玩家 token 认领席位的兼容接口可以保留，但只执行 `open → claimed`，不再自动开局。若它认领了有有效邀请的席位，该邀请在同一提交中失效。

### 4.6 公共状态与稳定错误

公共席位状态使用 `phase`，不再同时暴露容易矛盾的 `joined` 和 `ready` 布尔值。客户端按版本应用响应和 SSE 快照。

后端与客户端共享稳定错误码：

| 错误码 | 含义与恢复方式 |
|---|---|
| `INVITE_INVALID` | 邀请格式错误或不存在；重新核对输入 |
| `INVITE_EXPIRED` | 邀请已过期；由管理员重新生成 |
| `INVITE_CONSUMED` | 另一兑换 ID 已使用该邀请 |
| `SEAT_NOT_OPEN` | 席位已经被认领 |
| `SEAT_NOT_CLAIMED` | 未认领席位不能准备 |
| `MATCH_NOT_READY` | 对局尚未开始，不能行动 |
| `MATCH_ALREADY_STARTED` | 开始后不能改准备或认领 |
| `STALE_STATE` | 用响应携带的最新状态重新决策，不重放旧行动 |
| `TURN_EXPIRED` | 截止时间已到，后端已结算结果 |
| `ALREADY_BOUND` | 当前 DSH Session 已绑定未结束对局 |
| `BINDING_NOT_INHERITED` | fork 或 subagent 不继承父 Session 的席位 |

错误内容不包含邀请码、玩家 token、认证头或原始认证响应正文。

## 5. 前端产品流程

前端按用户当前任务只显示一个主要阶段。

### 5.1 未进入对局

提供三个明确入口：

- 创建对局，并可在创建时认领自己的席位；
- 输入邀请码认领席位；
- 输入对局 ID 只读观战。

直接输入 `matchId + playerToken` 移到标记清楚的“高级兼容入口”，不作为正常用户流程。成功进入后隐藏创建和加入表单；切换对局必须显式离开当前视图，避免误操作到旧对局。

### 5.2 等待阶段

- 左右席位以可见文字展示 `开放`、`已认领`、`已准备`，不只依赖颜色。
- 当前用户的身份和席位始终可见。
- 已认领控制者可以准备或取消准备。
- 管理员可为开放席位生成、复制或替换通用邀请。复制内容可直接是“加入邀请码 ABCD-EFGH 并开始”。
- 邀请用于人类、MCP 或 DSH，不在界面上标为“Agent 专用”。
- 邀请兑换、过期或席位由其他方式认领后，界面根据新的服务端状态移除可用提示。

### 5.3 进行阶段

页面主区域只保留棋盘、当前行动方、剩余时间、双方墙数和必要的行动反馈。准备、创建和邀请控件离开主流程。客户端不能以本地计时器自行判负；倒计时归零后等待后端确认结果。

### 5.4 结束阶段

显示胜负原因、完整棋谱和“创建新对局”入口。棋谱必须从 `/record` 的权威 actions 生成，不能继续使用页面打开以后逐次收集的 `lastAction` 代替完整历史。

### 5.5 前端状态组织

使用单一顶层状态对象，避免当前多个彼此独立变量产生跨对局残留：

```js
{
  identity: {
    matchId,
    role,
    seat,
    adminToken,
    playerToken
  },
  snapshot,
  record,
  connection: "connecting" | "live" | "reconnecting",
  pending: null | "claim" | "ready" | "action",
  ui: {
    actionMode,
    wallOrientation
  }
}
```

本地存储只保存恢复当前视图所需的最少身份字段，不保存对手凭证。管理员身份与席位身份并列存在，不互相推导。

SSE 只负责通知“可能有更新”。刷新采用 single-flight；收到多个更高版本时只拉取并应用最新版本。旧请求的错误或低版本响应不得覆盖已经成功应用的新状态。

### 5.6 棋盘可访问性

- SVG 不再把整个棋盘声明为 `role="img"` 后在内部嵌套可交互按钮。
- 键盘使用一个棋盘焦点：方向键移动预览位置，切换移动或墙方向，Enter 确认，Escape 取消。
- 不创建约两百个墙位 tab stop；鼠标和触摸仍可直接点选目标。
- 状态变化有可读文字和适度的 live region 通知；行动后焦点回到棋盘或明确结果区域。
- 尊重 `prefers-reduced-motion`，动画不承担唯一的信息表达职责。

## 6. 共享 Agent Client

在 Ball Chess 仓库提取协议无关的 Agent Client，供 MCP 服务和 DSH 插件共同使用。它负责：

- HTTP 认证、请求、错误映射和 expectedVersion；
- SSE 订阅、断线重订阅、取消和读取权威快照；
- 邀请兑换、准备、读取状态和提交行动；
- ASCII 棋盘、压缩合法行动和面向 Agent 的恢复提示。

它不复制棋局规则，不在客户端判断行动最终是否合法，也不持有进程全局席位。MCP 与 DSH 只适配各自的工具生命周期和秘密存储，避免两套接入实现逐渐产生不同语义。

## 7. MCP 接入

模型可见工具为：

| 工具 | 职责 |
|---|---|
| `join_by_invite` | 兑换当前 Agent 的席位邀请 |
| `set_ready` | 在等待阶段准备或取消准备 |
| `get_match_state` | 读取 ASCII 棋盘、席位和压缩行动信息 |
| `wait_for_turn` | 等待可行动、结束、取消或致命错误 |
| `submit_action` | 携带 expectedVersion 提交一个行动 |

预绑定入口继续使用 `--match` 与环境变量中的玩家 token，供测试、自动化和恢复使用；预绑定模式隐藏加入工具。任何模式都不把 playerToken 作为模型可填写的工具参数。

`wait_for_turn` 内部通过 SSE 等待并自动重订阅。心跳、短暂断线和无状态变化不返回模型；只在轮到自己、对局结束、调用被取消或发生不可恢复错误时结束。取消必须关闭订阅和挂起请求。

`submit_action` 成功时给模型的文本仅保留下一次决策所需信息；程序客户端仍可从结构化结果读取完整状态。失败时返回最新版本和明确恢复动作，Agent 不应盲目重放旧请求。

通用 MCP 的隐式绑定必须做串行或 single-flight 保护，防止两个并发 `join_match` 请求分别成功后由后返回者悄悄覆盖当前绑定。

## 8. DSH 插件与 Agent 预设

### 8.1 方案选择

实现一个 Ball Chess 专用 Cordis 插件，直接复用共享 Agent Client。插件通过 `ToolExecution.agent.id` 识别当前 DSH Session；不为每个 Session 启动 MCP stdio 子进程，也不修改通用 `dsh-mcp-client`。

这种结构保留一个协议实现，减少进程管理和重连层次。MCP 服务仍是外部客户端入口，DSH 插件则是同仓库内共享库的直接消费者。

### 8.2 凭证记录

插件使用 DSH credentials 服务，以 `ball-chess/s-<sha256(sessionId)>` 为键保存版本化联合类型：

```json
{
  "version": 1,
  "state": "redeeming",
  "baseUrl": "http://127.0.0.1:7100",
  "inviteCode": "ABCD-EFGH",
  "redemptionId": "<128-bit random id>"
}
```

或：

```json
{
  "version": 1,
  "state": "bound",
  "baseUrl": "http://127.0.0.1:7100",
  "matchId": "m_example",
  "seat": "left",
  "playerToken": "<secret>"
}
```

发送兑换前先保存 `redeeming`，成功后原子替换为 `bound`，从长期记录删除邀请码。未知结果始终使用原 `redemptionId` 恢复，不能生成第二次兑换。

DSH 本地凭证服务防止秘密进入正常的模型与工具数据流，但不能阻止同一操作系统用户下拥有任意文件读取能力的恶意工具读取凭证文件。因此安全承诺限定为：官方最小预设和插件的正常路径不暴露长期 token，而不是把 credentials-local 描述为强隔离沙箱。

### 8.3 Session 生命周期

- **同一 Session 冷恢复：** 下一次用户 turn 读取 `redeeming` 或 `bound` 记录并恢复，不重新索要邀请码。
- **fork：** 不继承席位凭证。首次使用工具时返回 `BINDING_NOT_INHERITED`，要求用新的邀请明确认领。
- **subagent：** 不继承父 Agent 的席位；对局行动保持在原控制者中，避免两个 Agent 共享同一席位。
- **archive：** 取消正在等待的调用并释放网络资源，但保留凭证，便于恢复原 Session。
- **对局结束：** 工具先把最终结果返回当前模型调用，再删除长期玩家 token；非秘密的最后对局引用可以保留用于显示。
- **完整 DSH 重启：** 不自动唤醒模型。用户在原对话输入“继续对局”后再恢复等待或行动。

### 8.4 Agent 预设

预设只装配 Ball Chess 游戏工具和完成对局所需的最小能力，不启用 shell、文件系统、浏览器或任意代码执行工具。用户命令：

```text
加入邀请码 ABCD-EFGH-JKLM 并开始
```

触发以下行为：

1. 调用 `join_by_invite`；
2. 调用 `set_ready({ ready: true })`；
3. 调用 `wait_for_turn`；
4. 轮到自己时依据最新状态选择一个行动并调用 `submit_action`；
5. 重复等待和行动直到结束。

`STALE_STATE`、非法行动或超时后先读取响应携带的最新状态再决策，不能自动重放旧行动。对手尚未准备时只等待，不伪造“已开始”。

插件、预设 overlay、安装说明和测试都位于 `ball_chess` 仓库。启动形式为 DSH 支持的 profile/overlay 入口，例如：

```powershell
pnpm dsh web --patch E:\My_project\ball_chess\dsh\ball-chess.overlay.yml
```

不修改 `deepseek-harness` 核心源码，也不要求用户从某个临时分支启动 DSH。

## 9. 验证方案

### 9.1 后端与持久化

- 截止时间前、恰好等于截止时间、截止时间后提交行动，验证 `now >= deadline` 时超时优先。
- 保存失败不改变内存、计时器和通知；单个通知失败不改变已提交结果。
- 对席位阶段、startedAt、deadline、结果和版本做不变量属性测试。
- v1 的 waiting、playing、finished、无行动进行中和矛盾记录分别迁移验证。
- 重放结果与持久化结果矛盾时拒绝加载，不覆盖原记录。
- 邀请生成替换、过期、并发兑换、响应丢失重试、不同兑换 ID 冲突和重启恢复。
- 同一 redemptionId 在邀请码过期、对局结束或席位状态变化后仍返回原成功结果。
- 第二个 ready 只提交一次开局状态；重复 ready 不增加版本。

### 9.2 前端

- 未进入、等待、进行、结束四阶段的主流程和可见控件。
- 创建并认领、通用邀请码加入、只读观战和显式切换对局。
- 只持久化自己的身份，不展示或保存另一个席位 token。
- SSE 快照合并、single-flight 刷新和旧错误不覆盖新成功。
- 刷新后从 `/record` 还原完整棋谱，而不是只显示本页收到的 lastAction。
- 键盘完成移动和放墙，tab 顺序不会遍历全部墙位；焦点和 reduced-motion 行为可验证。

### 9.3 MCP 与 DSH

- 通用 MCP 两个并发加入请求不能覆盖绑定。
- 预绑定入口保持可用且不暴露加入工具。
- `wait_for_turn` 在心跳和断线重连时不产生无意义的模型轮次，在可行动、结束和取消时返回。
- 工具文本、结构化结果、Session 事件和普通日志均不包含 playerToken。
- 两个 DSH Session 用同一预设分别绑定左右席位，凭证和状态相互独立。
- `redeeming` 与 `bound` 两种冷恢复；完整 DSH 重启后不主动调用模型。
- fork、subagent 和 archive 按既定生命周期处理。
- 两个 Agent 自动完成一局，以及 Agent 与人类使用同一 ready 状态机完成一局。

除单元和集成测试外，产品用户可见变化应增加浏览器端到端覆盖；Agent 工具的模型可见输出固定为可审阅的 snapshot，避免以后无意把秘密或冗长状态重新暴露给模型。

## 10. 分阶段实施

### 阶段一：正确性基础

- 修复截止时间后的行动仍可落子。
- 统一对局命令串行化和提交管线，隔离通知失败。
- 严格验证、重放和加载记录。
- 修复通用 MCP 并发绑定覆盖。

这一阶段先建立后续状态迁移可信赖的基础，不改变最终用户加入流程。

### 阶段二：席位状态机、邀请与准备

- 引入 v2 记录、迁移和派生 status。
- 实现创建时可选认领、通用邀请、幂等兑换和 `/ready`。
- 移除“第二席位加入即开局”。
- 完成稳定错误码和公共状态投影。

### 阶段三：前端任务流程

- 重组为四阶段界面。
- 接入通用邀请和准备。
- 使用单一前端状态对象、SSE 合并和权威棋谱。
- 完成棋盘键盘操作与可访问性修正。

### 阶段四：共享 Agent Client 与 MCP

- 提取共享客户端。
- MCP 改用共享客户端并加入邀请、准备、等待和紧凑输出。
- 保留并验证预绑定兼容入口。

### 阶段五：DSH 插件与预设

- 实现按 Session 存储的 Cordis 插件和生命周期。
- 提供最小 Agent 预设与 overlay。
- 完成双 Agent、Agent/人类和冷恢复端到端验证。

每阶段都应独立保持现有仓库可运行，不把未完成的跨阶段假设暴露为默认产品流程。

## 11. 完成判定

以下条件全部满足时，方案实现完成：

1. 后端在截止时间、并发命令、保存失败和通知失败下仍有唯一权威结果。
2. v1 记录可安全迁移，矛盾记录被拒绝且原文件不被覆盖。
3. 人类、MCP 和 DSH 使用同一种明确席位邀请；加入不再触发开局。
4. 两个已认领席位都 ready 后才原子开始，断线不改变认领或准备。
5. 前端清晰呈现创建、等待、进行、结束流程，并从权威棋谱恢复历史。
6. 键盘和触摸都能完成棋局，页面不产生数百个键盘焦点。
7. MCP 与 DSH 复用同一个 Agent Client，协议语义和错误恢复一致。
8. 两个 DSH Session 能分别控制左右席位；fork 和 subagent 不继承绑定；重启后可由用户继续。
9. 长期玩家 token 不进入模型输入、工具输出、Session 日志、普通日志或公共状态；安全说明不夸大本地凭证存储的隔离能力。

# Ball Chess 本地对局与 Agent 接入设计

- 日期：2026-10-24
- 状态：已在对话中逐节确认，待用户审阅书面文档
- 协议基础：v1
- 技术路线：单一 Node.js 本地服务、原生 SVG 前端、HTTP + SSE、MCP stdio 薄适配器

## 1. 目标

实现一个本地运行的双人棋类应用：双方从底边对称出发，通过移动和放墙争夺顶边。人类、程序化 bot 和大模型 agent 可以任意占据两个席位，包括两个不同的大模型 agent 对战。

首版必须做到：

- 前端不使用第三方运行时依赖，不需要打包或编译。
- 服务端是唯一规则权威，所有客户端使用同一套行动与状态语义。
- 支持人类操作、agent 加入和纯观战，不为每种组合复制游戏模式。
- 大模型 agent 通过标准 MCP stdio 接入；程序 bot 通过 JSON API 接入。
- 对局可以恢复、导出和测试，不依赖数据库或账号系统。

## 2. 已确认的棋盘与胜负规则

### 2.1 坐标与开局

- 棋盘为 9 列 × 13 行。
- 格子坐标记为 `(x, y)`，左下角为 `(0, 0)`，右上角为 `(8, 12)`。
- `x` 向右增加，`y` 向上增加。
- 左席位从 `(2, 0)` 出发，即从左数第 3 格。
- 右席位从 `(6, 0)` 出发，即从右数第 3 格。
- 默认左席位红色、右席位蓝色；颜色只是展示身份，不影响规则。
- 默认左席位先手。创建对局时可指定右侧或随机；随机结果在创建时确定并写入棋谱。
- 任一玩家到达 `y = 12` 的任意格子立即获胜，不需要到达特定列。

### 2.2 回合与移动

- 双方轮流行动，每次必须选择一次移动或一次放墙，不能主动跳过回合。
- 移动方向只能是 `up / down / left / right` 之一，每次一格；其中 `up` 使 `y + 1`。
- 不能移出棋盘、穿过墙或进入对方所在格。
- 不允许跳棋、斜走、交换位置或穿过对方。
- 有效移动或放墙都使 `plies + 1`，并交换行动方。
- 非法行动不改变棋盘，不增加 `plies`，也不交换行动方。

### 2.3 墙的基本规则

- 墙位于格子之间的网格缝，不占据格子。
- 每块墙覆盖连续两条单位格边，分横向 `h` 和纵向 `v`。
- 墙永久保留，不能移动或拆除。
- 墙不能越界、重叠或发生墙身十字交叉。
- 同向墙可以首尾连接；端点接触和合法 T 形连接允许。连续同向墙仍按多块独立墙记录。
- 放墙后，双方都必须仍能从各自当前位置到达顶行至少一个格子，否则该放墙非法。
- 路径检查只把墙视为永久阻挡，不把对方棋子视为永久障碍；对方棋子的实时占位在移动校验中单独处理。
- 允许放墙增加自己的路径长度，只要双方仍各有一条路径。

### 2.4 墙数量参数

创建配置使用 `wallLimit`：

- 默认 `null`，表示双方无限墙。
- 非负整数表示每方最多可放的墙数；`0` 表示双方只能移动。
- `wallsUsed` 始终记录各方已经放置的墙数，用于有限墙校验、展示和统计。
- 无限墙不代表可以重叠、交叉或绕过路径规则。

### 2.5 行动上限、无行动与超时

- `maxPlies` 默认 300，可配置为正整数。
- 每次有效行动后先检查是否到达顶边；若未获胜且 `plies >= maxPlies`，对局以 `max_plies` 判和。因此第 300 次行动到达顶边仍然是胜利。
- 若轮到一方时其合法行动列表为空，则该方判负，对方以 `no_legal_action` 获胜。此条是为避免协议死锁补充的边界规则，需在书面审阅时特别确认。
- `turnTimeoutMs` 默认 `null`，表示不限制单次思考时间。
- 若配置了正整数，当前行动方必须在时限内提交有效行动；超时则当前方判负，对方以 `turn_timeout` 获胜。
- 非法行动、断线、SSE 重连和页面刷新不暂停回合计时。
- 管理员主动中止使用独立结果 `aborted`，不记作任一方获胜。

## 3. 行动协议 v1

### 3.1 移动

```json
{ "type": "move", "direction": "up" }
```

`direction` 只能是 `up / down / left / right`。

### 3.2 放墙

```json
{ "type": "place_wall", "orientation": "h", "x": 1, "y": 5 }
```

横墙 `h`：

- 锚点范围：`x = 0..7`，`y = 1..12`。
- 从网格点 `(x, y)` 延伸到 `(x + 2, y)`。
- 阻挡第 `x`、`x + 1` 两列在第 `y - 1` 与第 `y` 行之间的移动。

竖墙 `v`：

- 锚点范围：`x = 1..8`，`y = 0..11`。
- 从网格点 `(x, y)` 延伸到 `(x, y + 2)`。
- 阻挡第 `y`、`y + 1` 两行在第 `x - 1` 与第 `x` 列之间的移动。

例如横墙 `(1, 5)` 与 `(3, 5)` 可以首尾连接，视觉上形成连续长墙，棋谱中仍是两次独立放墙。

服务端内部把墙转换为被阻挡的相邻格子边。相同方向墙若共享任一单位边则重叠；相对方向墙仅在墙身穿过墙身时判交叉，端点接触不判交叉。客户端不需要计算这些内部边。

## 4. 总体架构与模块边界

```text
浏览器（人类操作 / 观战） ── HTTP + SSE ──┐
程序化 bot ─────────────── HTTP + SSE ─┤
                                          ▼
                                    Node 对局服务
                                          │
                                          ▼
                                     纯规则引擎
                                          ▲
Kimi / Claude / Codex                     │
        ⇅ MCP stdio                       │
     MCP 适配器 ─────────── HTTP + SSE ───┘
```

### 4.1 纯规则引擎 `core/`

独立 ES Module，不访问网络、文件或 DOM，负责：

- 创建初始局面。
- 枚举和校验移动、放墙。
- 将墙映射为格子邻接限制。
- 使用 BFS 或等价搜索验证双方到顶边的路径。
- 应用有效行动、切换行动方并判断结果。
- 输出确定性的、可 JSON 序列化的状态。

浏览器可以复用规则引擎做合法位置预览，但服务端必须独立重新校验每次行动。

### 4.2 对局服务 `server/`

- 使用 Node.js 22+ 和内置 `node:http`、`node:test` 等能力。
- 提供静态页面、JSON API、SSE、房间生命周期、令牌校验和本地持久化。
- 使用完整状态快照，不实现增量棋盘补丁。
- 不引入 Express 或 WebSocket。行动使用请求—响应式 POST，状态推送是单向 SSE，二者足够覆盖首版需求。
- 默认绑定 `127.0.0.1:7100`；`npm run dev -- --host <host> --port <port>` 必须能转发并应用命令行参数。

### 4.3 原生前端 `web/`

- 使用 HTML、CSS、原生 JavaScript 和 SVG。
- 不使用前端 npm 包、在线字体、图片服务、CSS 框架或打包器。
- 浏览器可直接加载 ES Module；只允许静态服务暴露 `web/` 和需要共享的 `core/` 文件，不能暴露令牌、运行数据或项目其他文件。
- 网络请求以服务端结果为最终显示依据，不做未确认的乐观落子。

### 4.4 MCP 适配器 `mcp/`

- 使用官方 MCP SDK，是首版唯一必需的第三方包。
- 每个 agent 启动独立 stdio 进程；进程内只保存一个对局会话。
- 适配器不复制规则，不保存另一份权威棋盘，不替 agent 选棋。
- 相同 `matchId + playerToken` 重复加入视为重连；一个已加入进程不能无提示地切换到另一对局或席位。
- 不支持 MCP 的程序可直接使用 HTTP API，因此两类客户端没有对局语义分叉。

## 5. 对局状态

公共状态采用以下结构；示例值仅用于说明字段：

```json
{
  "matchId": "m_example",
  "version": 12,
  "status": "playing",
  "config": {
    "width": 9,
    "height": 13,
    "wallLimit": null,
    "maxPlies": 300,
    "turnTimeoutMs": null,
    "firstPlayer": "left"
  },
  "players": {
    "left": { "color": "red", "position": [2, 0], "wallsUsed": 3 },
    "right": { "color": "blue", "position": [6, 0], "wallsUsed": 2 }
  },
  "walls": [
    { "orientation": "h", "x": 1, "y": 5 }
  ],
  "currentPlayer": "left",
  "plies": 12,
  "lastAction": null,
  "result": null
}
```

字段约定：

- `status`：`waiting / playing / finished`。
- `version`：创建时为 0；席位首次加入、双方就绪、有效行动和结束等权威状态变化时递增。单纯重连、读取状态或 SSE 重订不递增。
- `plies`：只计算有效移动和放墙，不包含加入、非法行动、中止或超时事件。
- `lastAction`：记录最近一次有效行动的玩家、行动和对应序号；初始为 `null`。
- `firstPlayer`：服务端归一化后的实际先手，不再保留未决定的 `random`。
- `result`：未结束为 `null`；结束后包含 `kind`、`winner` 和 `reason`。
- 获胜结果 `kind = "win"`；行动上限和棋 `kind = "draw"`；管理员中止 `kind = "aborted"`。
- 玩家令牌、管理员令牌和 MCP 会话永远不出现在公共状态、SSE 或导出棋谱中。

带有效玩家令牌的 `state` 响应额外包含：

- `yourPlayer`：`left / right`。
- `yourTurn`：当前是否轮到该席位行动。
- `legalActions`：仅在自己的有效行动回合提供完整合法行动对象列表；其他情况为空数组。

MCP 还返回 ASCII 棋盘，帮助大模型理解空间关系；ASCII 只是展示，JSON 才是提交行动的依据。

## 6. HTTP 与 SSE 接口

| 接口 | 认证 | 用途 |
|---|---|---|
| `POST /api/matches` | 本地创建请求 | 创建对局，返回 `matchId`、`adminToken` 和两个 `playerToken` |
| `POST /api/matches/:id/join` | 玩家 Bearer token | 加入或重连席位，可附带显示名和客户端类型 |
| `GET /api/matches/:id/state` | 可选玩家 Bearer token | 获取公共状态；带玩家令牌时附带席位视角信息 |
| `POST /api/matches/:id/actions` | 玩家 Bearer token | 提交 `expectedVersion + action` |
| `POST /api/matches/:id/abort` | 管理员 Bearer token | 中止对局；管理员令牌不能用于走棋 |
| `GET /api/matches/:id/events` | 本地只读 | SSE 推送公共状态快照 |
| `GET /api/matches/:id/record` | 本地只读 | 导出移除所有令牌的棋谱 |

提交行动正文：

```json
{
  "expectedVersion": 12,
  "action": { "type": "move", "direction": "up" }
}
```

SSE 约定：

- 每次权威状态变化发送一份完整公共快照，事件 ID 使用对应 `version`。
- 客户端记录已经显示的版本，忽略较旧快照。
- SSE 重连后必须再拉取一次最新状态，避免遗漏断线期间的事件。
- 观战是本地只读能力；任何令牌都不能通过 SSE 获取。

## 7. MCP 工具

首版只提供四个工具：

| 工具 | 输入与行为 |
|---|---|
| `join_match` | 输入 `matchId + playerToken`，可附带显示名；加入后由当前 stdio 进程保存会话 |
| `get_match_state` | 返回 JSON 状态、ASCII 棋盘、`yourTurn` 和当前合法行动 |
| `wait_for_turn` | 等待自己的回合或结束；默认等待 10 秒，单次上限 15 秒，超时返回 `waiting: true` 而非错误 |
| `submit_action` | 输入 `expectedVersion + action`；返回新状态，或结构化错误、最新状态和合法行动 |

`wait_for_turn` 的超时只是单次工具调用的等待边界，不等于棋局回合计时。agent 应继续等待，直到轮到自己或游戏结束。

给 agent 的提示词要求其执行以下循环：

```text
等待自己的回合 → 读取 JSON 棋盘和合法行动 → 选择一步 → 提交
→ 若被拒绝则读取最新状态并重新选择 → 直到对局结束
```

平台不启动第三方 agent，不持有模型 API 密钥，也不替不同厂商做专属决策适配。

## 8. 对局生命周期与错误恢复

1. 创建对局并返回一个管理员令牌和两个独立玩家令牌。
2. 创建者操作一个席位，或以观战者身份把两个席位都交给 agent/bot。
3. 每个席位凭令牌加入；同一令牌重复加入是幂等重连。
4. 两个不同席位首次就绪后开始，按实际先手行动。
5. 服务端在状态副本上校验并应用行动，成功持久化后才替换内存状态并广播。
6. 到达顶边、行动上限、无合法行动、回合超时或管理员中止后进入 `finished`，不再接受行动。

行动相关错误至少包括：

| 错误码 | 含义与恢复方式 |
|---|---|
| `NOT_YOUR_TURN` | 尚未轮到该席位；等待并重新读取状态 |
| `STALE_STATE` | `expectedVersion` 已过期；读取最新版本后重新决策，不能盲目重放旧行动 |
| `ILLEGAL_ACTION` | 行动不合法；附带具体原因和最新合法行动 |
| `MATCH_FINISHED` | 对局已结束；返回最终结果 |
| `MATCH_NOT_FOUND` | 对局不存在或标识错误 |
| `STORAGE_ERROR` | 状态未能可靠保存；该行动不被视为已接受 |

认证失败、权限不足和请求格式错误使用独立错误码及相应 HTTP 状态。所有行动拒绝都不推进棋盘、版本或回合计数。

若行动已生效但响应在网络中丢失，重试旧版本会得到 `STALE_STATE`；客户端通过最新 `lastAction` 和版本识别该情况，不会重复落子。

## 9. 本地持久化与安全边界

### 9.1 持久化

每局使用一个内部 JSON 文件：

```text
data/matches/<matchId>.json
```

文件包含配置、实际先手、令牌、有效行动、时间戳、回合截止时间和结果。每次有效行动通过临时文件加替换的方式原子写入；服务启动时重放记录并重建状态。

- 回合计时按持久化的截止时间恢复，而不是重启后重新获得完整思考时间。
- 连接状态属于临时状态，重启后等待客户端重连。
- 对外 `record` 导出始终移除令牌。
- 损坏记录不被自动覆盖；该对局标记为不可恢复并记录错误，不影响其他对局。
- `data/matches/` 加入 `.gitignore`，避免把本地对局和令牌提交到版本库。

### 9.2 本地安全默认值

- 默认只绑定 `127.0.0.1`。
- 玩家和管理员令牌至少包含 128 位随机熵，不写入日志。
- 静态文件只允许访问明确公开的前端和共享规则文件。
- 请求体限制为合理的小体积 JSON，拒绝未知行动类型和多余坐标范围。
- 首版不开放 CORS，不承诺公网部署安全；显式修改监听地址不意味着已经获得公网加固。

## 10. 前端交互与视觉设计

### 10.1 页面与操作

首版为单页应用：

- 顶部显示当前回合、双方墙数、行动次数、剩余时间和连接状态。
- 中间是 9 × 13 SVG 棋盘；窄屏时侧栏移到棋盘下方。
- 移动模式显示合法落点；放墙模式提供横/竖切换、网格缝上的合法性预览和提交反馈。
- 等待对方或观战时锁定操作控件。
- 侧栏提供创建/加入、席位状态、agent 接入信息、最近行动和最终结果。
- 双方均为 agent 时自动呈现观战模式，不显示当前用户不可用的走棋控件。
- 为每个 agent 席位提供可复制的 MCP 配置、房间令牌和启动提示词。
- 尊重 `prefers-reduced-motion`，关键状态不只依靠颜色表达。

### 10.2 美术方向：A · 现代拟物 / Soft Industrial

采用已确认的浅色现代拟物方向，而不是 2010 年左右的纹理堆叠式拟物。

保留：

- 当代桌面产品般的材质、接触关系和统一环境光。
- 近白哑光树脂棋盘、缎面珐琅小球、圆角漆面墙。
- 极淡薄荷绿目标区、低对比网格、充分留白。
- 柔和且有明确方向的接触阴影和边缘厚度。

去除：

- 木纹、皮革、拉丝金属背景。
- 镜面大高光、厚黑阴影、多层描边和强内阴影。
- 立体按钮、夸张弹性、外发光和粒子效果。

只有棋盘、球和墙使用材质深度；按钮、侧栏和文字保持现代平面排版。

### 10.3 物件比例与净空

以 SVG 中的一格边长 `s` 为统一尺寸基准：

- 小球直径为 `0.625s`。
- 墙顶面厚度为 `0.1875s`，侧面深度约为 `0.0625s`。
- 墙覆盖长度严格为 `2s`，不能为了视觉效果缩短规则范围。
- 当 `s = 24px` 时，球直径为 `15px`，墙顶面厚度为 `4.5px`，侧面约为 `1.5px`，墙长为 `48px`。
- 球、墙和阴影使用同一组尺寸变量，不允许分别凭感觉缩放。
- 相邻格球与墙之间必须保留可见空隙；阴影扩散同步收敛，避免物件不碰但投影重叠。

基准色可使用：页面 `#E9EDEA`、棋盘表面 `#F5F7F4`、网格 `#D4DBD6`、红球 `#D45A62`、蓝球 `#5689B6`、目标区薄荷绿 `#B9E5D1`。渐变只用于表达材质，不改变整体色彩识别。

移动和放墙反馈使用约 160–220ms 的短动画；减少动态效果偏好下取消非必要位移和过渡。

## 11. 测试与验收

使用 Node 内置 `node:test`，不额外引入测试框架。

### 11.1 规则测试

- 初始坐标、先后手、四向移动和顶边胜利。
- 越界、占格、无跳跃和无斜走。
- 横竖墙锚点范围、单位边映射、连续连接、端点接触、重叠和十字交叉。
- 放墙后双方路径；对方棋子不被误当成永久路径障碍。
- 无限墙、有限墙和零墙配置。
- 第 300 次行动获胜与达到上限判和的顺序。
- 无合法行动、回合超时和管理员中止。
- 任意有效行动后的不变量：双方不同格、双方各有到顶边路径、行动方正确、`plies` 正确。

### 11.2 API 与持久化测试

- 令牌越权、管理员与玩家能力隔离。
- 重复加入、旧版本行动、响应丢失后的安全重试。
- 非法行动不改变版本或棋谱。
- SSE 快照、断线重连后状态校正。
- 完整对局、服务重启恢复、超时截止恢复和损坏记录处理。
- 导出棋谱不包含令牌，静态路径不能读取运行数据。
- 测试使用临时数据目录，不污染真实对局。

### 11.3 MCP 与端到端测试

- 两个独立 stdio 客户端完成加入、等待、行动和结束。
- 非法行动后能获得最新状态并纠正。
- 两个不同决策逻辑的模拟 agent 自动下完一局。
- 提供一个不依赖第三方包的示例程序 bot，演示 HTTP 加入、轮询和提交合法行动。

浏览器验收覆盖移动、横竖放墙、连续墙、观战、响应式布局、SSE 重连和现代拟物物件的相邻净空。

第三方大模型 agent 通过标准 MCP 接入；首版不声称已经逐一验证所有厂商客户端。

## 12. 首版范围外

以下能力不进入首版：

- 账号、公网部署和公网安全加固。
- 内置 AI 或自动启动第三方大模型 agent。
- 排行榜、锦标赛、ELO 和批量训练平台。
- 图形化复盘编辑器。
- 原生移动应用、数据库和微服务拆分。

完整棋谱、清晰席位模型和独立规则引擎为这些后续能力保留扩展空间。

## 13. 完成判定

首版只有同时满足以下条件才算完成：

1. `npm run dev` 能启动本地服务，并能转发 host/port 参数。
2. 浏览器可以直接创建、操作和观战，前端没有第三方运行时依赖。
3. 所有已确认规则及边界测试通过。
4. 两个独立模拟 agent 能通过相同协议完成一局，非法行动不会破坏状态。
5. MCP stdio 客户端可以完成加入、等待、行动和结束。
6. 对局能够导出并在服务重启后恢复，导出内容不泄露令牌。
7. 前端呈现已确认的现代拟物方向，球和墙在相邻位置没有视觉重叠。
